## Problem Statement

> Archived reference. Observations, proposed work and source paths describe the original dated snapshot. Use the [release checklist](../../release-checklist.md) for current requirements.

Shards of Affinity currently presents its turn-based battles through character cards and battle events. Players need to experience those same battles as a readable, animated 3D battlefield while retaining the game's existing characters, spells, targeting rules, and server authority.

The prototype must support active fighting: the player chooses a spell and legal targets, explicitly commits with Cast, sees the actual result on those targets, and continues through enemy turns to victory or defeat. A target selector beside a recording cannot establish that this interaction works. The current battle hook also submits automatically when enough targets are selected, which conflicts with the required opportunity to review a choice before casting.

The first objective is technical feasibility: prove the live interaction, event presentation, imported animation pipeline, and desktop runtime behavior. Comparing visual alternatives and evaluating deeper gameplay feel follow that proof.

## Solution

Add a development-only Three.js battle presentation within the existing authenticated battle screen. Reuse its WebSocket connection, legal-target requests, Cast command, server game logic, character ownership, encounter entry, and battle results. Keep the current battle view available.

Present up to two party characters on the left and four enemies on the right as stylized dark-fantasy miniatures under a fixed elevated camera. Names, HP, and status markers sit beside each entity; turn order sits above the scene; spells sit below; and a side inspector contains mana, cooldowns, and full effect descriptions. Mouse and keyboard controls share the same selection state.

The player selects a spell, chooses a legal target or accepts the complete automatically selected self/team target set, and presses Cast. The server resolves that choice, and the scene presents the returned results. Use restrained animation, approximately one-second ordinary actions, speed controls, and reduced motion. Audio and mobile qualification are outside this milestone. Clearly identified model stand-ins are acceptable while proving one real imported animation pipeline.

## User Stories

1. As a player, I want to open a 3D presentation of my existing battle, so that I can fight using my current characters and game session.
2. As a player, I want to switch between the current view and the 3D view without starting a different battle, so that I can compare and recover presentations safely.
3. As a player, I want my chosen spell and targets to determine the server's actual combat result, so that my decisions matter in the battle.
4. As a player, I want enemies to respond under the existing game rules, so that I can play an encounter through to victory or defeat.
5. As a character owner, I want to act only for my own character when its turn arrives, so that ownership and turn order remain consistent with the existing game.
6. As a spectator, I want to inspect and watch a battle without being able to submit another player's actions, so that observing it remains read-only.
7. As a player, I want to see the active character and upcoming turn order, so that I know who is acting and can plan ahead.
8. As a player, I want to inspect spell availability, mana cost, and cooldown before committing, so that I understand which actions I can take.
9. As a player, I want choosing a spell to reveal its current legal targets, so that I can select a valid recipient.
10. As a player, I want to choose any legal entity for a single-target spell, so that I control whom the spell affects.
11. As a player, I want self-targeted spells to select the caster automatically, so that I do not need a redundant target click.
12. As a player, I want whole-team spells to select and highlight the complete legal team, so that I understand everyone who will be affected.
13. As a player, I want the selected spell and target names to remain visible before casting, so that I can review my intended action.
14. As a player, I want to change or cancel a prepared selection, so that I can reconsider before spending my turn or resources.
15. As a player, I want an explicit Cast button, so that selecting a spell or target alone never commits my action.
16. As a player, I want one press of Cast to submit one action and repeated clicks while it is pending to have no additional effect, so that I do not accidentally cast twice.
17. As a player, I want unavailable or invalid casts to remain disabled or be rejected without consuming my turn or resources, so that the controls do not punish an invalid request.
18. As a keyboard user, I want to inspect entities, select spells and targets, and activate Cast using ordinary controls, so that mesh picking is not my only way to fight.
19. As a player, I want inspecting an entity to be distinct from selecting it as a target, so that I can read enemy or fallen-entity details without changing my action.
20. As a player, I want every entity's name, HP, and status markers to remain readable, so that I can assess both teams at a glance.
21. As a player, I want mana, cooldowns, and full effect descriptions in a side inspector, so that exact combat details remain available without covering the battlefield.
22. As a desktop player, I want all six entities and the controls to remain readable when I resize the window, so that the scene works at the desktop sizes used for verification.
23. As a player, I want party members, enemies, the active entity, legal targets, and selected targets to have distinguishable markers, so that I do not have to infer state from color alone.
24. As a player, I want attacks and casts to identify their caster and affected targets, so that I can follow what happened.
25. As a player, I want damage, healing, and resource numbers to change at a consistent visual impact point, so that the feedback agrees with the action I see.
26. As a player, I want effect application, triggering, and removal to be visible, so that I can understand ongoing conditions without rereading the whole event history.
27. As a player, I want deaths to remain visually clear and fallen entities to stop appearing as actionable targets, so that the battlefield reflects the combat state.
28. As a player, I want animation speed and visual skipping to leave combat outcomes unchanged, so that faster presentation does not alter the game rules.
29. As a player, I want delayed animation to prevent stale casting controls while offering a bounded way to catch up, so that visual feedback cannot trap my next decision.
30. As a player, I want disconnection to disable casting and clear stale selection, so that I cannot unknowingly submit an obsolete action.
31. As a player, I want reconnection to restore the latest server state without automatically resending an uncertain cast, so that I can continue without duplicate actions or a long stale animation backlog.
32. As a player, I want outdated legal-target responses to be ignored, so that quickly changing spells cannot make the wrong targets appear valid.
33. As a player, I want repeated state updates to avoid repeating an attack, so that the animation accurately reflects the server's event history.
34. As a player, I want battle completion to lead into the existing result flow after bounded visual feedback, so that I can recognize victory or defeat and continue using the game.
35. As a replay viewer, I want play, pause, seek, and restart to affect only recorded presentation, so that watching a battle cannot submit actions or rewind a live encounter.
36. As a player who prefers reduced motion, I want clear results with restrained or disabled movement effects, so that I can understand combat comfortably.
37. As a player, I want a missing model or animation to have a readable fallback, so that an asset failure cannot prevent me from finishing a battle.
38. As a player, I want the existing battle controls available when the 3D renderer cannot initialize, so that a graphics failure does not remove command access.
39. As a player, I want repeated instances of the same miniature to animate and react independently, so that selecting or damaging one entity does not change its siblings.
40. As a player, I want repeated view entry and exit to avoid progressively increasing resource use, so that the prototype remains usable over multiple battles or view switches.
41. As a player, I want ordinary navigation to avoid loading the entire 3D scene and its assets, so that the prototype does not slow unrelated game screens.
42. As a maintainer, I want model provenance, clip mappings, and visual substitutions documented, so that the asset pipeline can be reproduced and replaced deliberately.
43. As a maintainer, I want repeatable starting snapshots, commands, and recorded results, so that targeting and presentation regressions can be checked without relying on mutable character reconstruction.
44. As a maintainer, I want reproducible launch instructions, desktop screenshots, and measured frame/load/resource behavior, so that I can judge whether this technical milestone is complete and choose the next experiment.

## Implementation Decisions

- **Existing game integration is the primary boundary.** Add a presentation option to the existing live battle screen and reuse its connection and authenticated session. Keep combat resolution, enemy behavior, turn progression, randomness, resources, effects, cooldowns, and victory/defeat in the existing server game logic. Do not add an alternate browser-local combat driver. The existing ownership rules determine whether the user controls one or both party characters.
- **Keep the current view usable.** Switching views changes presentation only; it must not create another battle, submit a command, or introduce a second connection for the same battle. Keep the prototype clearly marked and development-only, with lazy loading at the battle-view boundary and usable existing controls if graphics initialization fails.
- **Explicit Cast changes the interaction contract.** The existing battle hook currently casts when the selected target count reaches the requested count. Disable that behavior for the prototype and invoke the existing Cast command only from its button. Preserve the ordinary battle view's usability when adapting shared logic. Players can inspect, change, and cancel their spell/target selection before submission.
- **Use the server's legal-target contract.** Request targets for the current spell and turn. Single-target actions accept any one legal entity; self and whole-team actions automatically select their complete legal set and wait for Cast. Show the spell and selected target names in the HTML interface and the same selection in the scene. Inspection, hovering, and target selection remain separate. Random-target abilities are outside the first interaction qualification without changing their existing rules or inventing manual targets for them.
- **Prevent stale and duplicate commands.** Cast is enabled only when connected, caught up to current server state, on the active character owner's turn, with an available spell, a complete legal target selection, and no cast pending. Clear stale selection when spell, actor, legal targets, encounter, or connection changes. Correlate or serialize target requests so an old response cannot enable a new spell's Cast button. Rejections leave authoritative turn/resources intact and restore a usable current selection flow. Never automatically retry an uncertain cast after reconnecting.
- **Retain server validation.** Validate ownership, current turn, spell availability, legal target membership, and required target counts at the existing command boundary. The current server wrapper advances the turn after a rejected cast; qualify and isolate the smallest necessary correction. No new transport or database schema is planned. Any small compatible protocol change needed to distinguish stale requests or rejected commands must be justified as part of this existing boundary.
- **Keep presentation time separate from combat state.** The battle UI consumes authoritative state and ordered events. A small pure presentation adapter reconstructs display frames and visual cues; the scene animates them. Prefer adapting the existing battle hook and event reconstruction boundary over creating a parallel battle subsystem. Do not introduce a separate abstraction for every scene concern.
- **Preserve the existing event semantics.** Cover spell casts, effect triggers/removals, regeneration, cooldown changes, and death. Resolve caster identity from the initial spell-owner map and effect identity from tracked metadata. The current event envelope supplies round and event data, without explicit event sequence IDs or complete choreography. Result maps can aggregate hits or omit originally selected targets. Use generic visual cues when information is missing; never rerun spell calculations to manufacture animation detail. Preserve existing Map/serialization semantics when normalizing recorded data.
- **Handle history updates coherently.** An identical accepted history adds no new attack; an appended suffix plays once; a shortened or divergent history cancels transient cues and reconstructs an appropriate display state. Scope local cue identity to an encounter/history revision rather than a spell ID, because a spell can be cast repeatedly. On reconnect or return after a long interruption, restore the latest authoritative state instead of playing an unbounded stale backlog.
- **Separate live controls from replay controls.** Live speed and skip controls affect only already resolved visuals. Replay play/pause, seek, and restart must never send combat commands or recreate a live battle. New battles use the existing encounter flow. Block stale input during pending visual presentation, but provide a bounded skip/fallback path. Preserve the existing result flow after a bounded final animation instead of treating its current fixed redirect timer as the animation scheduler.
- **Use the agreed desktop composition.** Start with a fixed elevated orthographic camera, stable formation slots, party left, and enemies right. Support up to two party characters and four enemies. Show names, HP, and status markers beside entities; turn order above; spells below; mana, cooldowns, and full effect descriptions in a side inspector. Use generous mesh hit areas, deliberate event propagation, visible focus/selection states, and equivalent keyboard-operable HTML controls. Positions and lunges have no tactical meaning.
- **Use restrained dark-fantasy miniatures.** Ordinary actions initially last approximately one second, with slightly longer major spells, modest lunges/projectiles, and a fixed camera. Treat those timings as presentation settings to judge in the browser. Include speed controls and reduced motion; defer audio. Color themes must not imply new elemental weaknesses or resistances.
- **Keep the current client stack.** Use stable React Three Fiber with Three.js/WebGL and standard materials, retaining React, Vite, and Bun. Add selected Drei helpers only where useful and compatible. The researched candidate is Three 0.186.0, React Three Fiber 9.7.0, and Three types 0.185.4; optional Drei is 10.7.8. These are candidates to validate and pin, not a claim of integrated runtime compatibility. Record the known Three/type revision mismatch and Drei declaration issues. If enabling shadows, use explicit PCF behavior appropriate to the selected release. Avoid broad dependency upgrades.
- **Prove one imported animation pipeline.** Use a free, clearly licensed miniature asset, with at least one real looping clip and one replayable one-shot clip exercised across four independent instances. One model may stand in for multiple game entities if labels/markers distinguish them and substitutions are identified. Maintain versioned GLB assets and a small visual manifest containing clip names, scale, facing, label height, and impact cues. Record the creator, source URL, exact asset/version, license and attribution terms, modifications, and export recipe where applicable. Prefer in-place clips. Procedural hit/death fallbacks are acceptable when documented, but do not replace the required imported clips.
- **Make resource ownership explicit.** Independently clone skinned hierarchies and maintain per-entity mixer/action state, while sharing immutable geometry, textures, and animation clips. Reset one-shot actions before replaying them. Isolate mutable materials or use independent markers so a flash on one entity does not affect siblings. Separate instance teardown from shared-cache eviction, including unique skeleton/material/effect cleanup and final-owner image resources where applicable. Neither a missing clip nor a failed model may block presentation indefinitely.
- **Use existing working content for verification.** Start with a small real encounter and valid player loadouts, then qualify a six-entity encounter and representative direct damage, healing, self/team targeting, effects, resources, cooldowns, and death. Capture initial builds/identities, spell ownership, effect metadata, commands, and resolved events. A seed alone is insufficient because identities and character reconstruction are not fully immutable. Keep recordings free of account secrets or tokens.
- **Keep gameplay repairs bounded.** Preserve current combat rules and explicitly identify any smallest baseline correction needed to make the selected command or content path work. In addition to invalid-cast turn advancement, effect-origin lethal damage and reconstruction/RNG side effects require attention when exercised. Avoid known fragile content where it is not needed for this slice; never conceal a rules defect with invented visual results.

## Testing Decisions

- **Primary seam: the existing battle screen and WebSocket command/result contract.** Exercise selection, explicit Cast, authoritative responses, turn progression, and visible outcomes through that boundary. Keep the real command handler and shared combat rules in integration coverage; do not replace the playable acceptance check with a mocked local battle. This follows the user's confirmed choice to reuse the current WebSocket and game logic. Avoid separate test-only production interfaces for every hook or mesh.
- **Test observable behavior.** A good test establishes a starting encounter, performs user commands, and checks emitted commands, authoritative outcomes, and visible state. Do not assert private helper calls, component structure, arbitrary snapshots of all markup, or that a mesh merely exists. Selecting without pressing Cast must emit no cast command; one Cast must target the selected legal entity and produce the corresponding server result.
- **Cover command and session behavior.** Check single, self, and complete-team selection; change/cancel before Cast; duplicate clicks; out-of-turn and non-owner commands; unavailable spells; invalid target/count requests; rejection without consuming resources or a turn; outdated target responses; disconnection; reconnect without automatic command resend; and spectator restrictions. Verify enemy progression and both victory and defeat. Test view switching without a duplicate connection or unintended mutation.
- **One supporting pure seam: event-to-display reconstruction.** Reuse or minimally extract the current reconstruction responsibility into the proposed adapter. Feed initial snapshots and histories through it and assert exact entity resources, cooldowns, effects, deaths, and cursor/final state. Cover identical, appended, shortened, and replaced histories; missing metadata with generic visual fallback; and the same recorded results at normal speed, accelerated speed, visual skip, and replay seek. Playback and inspection must not consume combat randomness or run spell calculations.
- **Prior art and test setup.** No automated test files were found in the indexed source, and the inspected package manifests define no test scripts or existing browser test runner. The current battle hook, stats timeline, and finished-battle viewer provide behavioral prior art, not an established automated suite. Add the smallest runnable checks around the above boundaries using the existing toolchain; document the exact commands. Do not build a general test framework as part of the prototype.
- **Real browser acceptance is required.** Complete a player-controlled battle over the development WebSocket, using mouse and keyboard controls, and verify chosen-target resolution, explicit Cast, exact feedback, active turn, effect updates, death, and result handling. Verify smaller and larger desktop windows and document their dimensions. Exercise reduced motion, failed/missing model and clip fallback, graphics fallback, disconnect/reconnect, replay seeking, and repeated scene entry/exit. Preserve the ordinary battle view and unrelated navigation.
- **Verify imported assets and independent instances.** Validate the GLB and required nonzero-duration clips, then inspect the actual model at the gameplay camera. Exercise four copies: one attack must not animate another; one selection/damage reaction must not tint another; repeated attacks restart; and death remains clear. Repeat mount/play/unmount or view-switch cycles after cache warm-up and verify that retained resource counts settle rather than grow without bound.
- **Measure technical feasibility honestly.** Run the relevant build and type checks for the chosen pinned dependency set. Record a six-entity encounter including its busiest effect on a named desktop device/browser, reporting sustained frame-time behavior and spikes, initial transfer/load cost, time to useful interaction, and resource-count trend. Aim for 60 fps as the research target; do not claim that target or other device/browser coverage without measurements. Measure rendering separately from network wait time. A stable intentional cache is acceptable; continually growing resources are not.

## Out of Scope

- A new battle engine, browser-local combat driver, alternative WebSocket service, or unauthenticated replacement game.
- Predetermined recordings or per-target canned outcomes as substitutes for actively playing the battle.
- Mobile/touch qualification, new multiplayer behavior, changed character ownership, or bypassed authentication.
- Tactical movement, grids, range, collision, cover, line of sight, action combat, changed party size, or new elemental combat rules.
- Dungeon/reward redesign, broad progression or balance changes, economy fixes, and unrelated content/gameplay repairs.
- Multiple competing UI variants in this milestone, a complete creature-specific model roster, custom art production, audio, free-orbit/cinematic cameras, WebGPU, or custom shader systems.
- Production deployment or production data changes. Use the existing local/development environment for implementation and verification.

## Further Notes

- The user confirmed this design after the interview. Priority is technical feasibility, then visual direction/readability, then deeper gameplay-feel evaluation. Active fighting through the existing game is part of the first priority.
- Work is intended for the existing `prototype` branch and checkout. Preserve the uncommitted documentation and tooling work. The repository overview, content catalog, Three.js research, handoff, decision log, and glossary contain supporting context; some are still local/untracked and will not appear in a checkout of the branch commit alone. This issue states the agreed requirements so they do not depend on those documents being published.
- Development entry points use the existing Bun/Doppler setup. Inspect available configuration and authenticated access before requesting user input. If external access is blocked, continue independent rendering and recorded-data verification, report the precise blocker, and leave live-battle acceptance explicitly incomplete. The same rule applies if a suitable licensed animated asset cannot be acquired: a graybox is useful progress but does not complete the imported-model milestone.
- Deliver the running preview URL, exact launch and usage instructions, desktop screenshots, a concise description of the implemented interaction, relevant source-change and test/build summaries, measured frame/load/resource evidence, asset provenance, and specific remaining gaps. Distinguish live fighting from replay. Do not claim completion on the basis of a successful build or prerecorded scene alone.
- Recommend the next milestone from the observed evidence: compare visual alternatives, improve the weakest combat interaction, or expand the verified asset/content pipeline. Connecting the existing WebSocket is already part of this milestone.
