## Scope and evidence limits

Reviewed server HTTP/tRPC entry points, context/authentication, character and dungeon operations, battle/chat Durable Objects, command validation, completion workflow, telemetry initialization, Wrangler configuration, client chat rendering and build environment handling. CodeGraph supplied structural context; current source supplied the exact checks. Local probes used synthetic users and the existing in-memory PGlite fixture, with no network/database credentials. The chat probe executed the real Durable Object class with only platform and Clerk boundaries replaced.

This review does not establish real Clerk session revocation, Cloudflare origin behavior, deployed resource isolation, retention settings, complete dependency exploit reachability, or staging recovery. The final dependency section records a bounded source review and the remaining disposition work. No production or staging writes, secret retrieval, or deployment occurred. No secret values belong in this report.

## Identity, origin and session facts

The upstream HTTP routes call Clerk middleware, read `getAuth(c)?.userId`, reject absent identity, and replace the forwarded URL's `userId` with `URLSearchParams.set`. Chat similarly overwrites `username` from the database. A user-supplied internal `userId` query parameter is **not** evidence of impersonation. Durable Object namespace RPC/fetch is reached through the trusted Worker route; public requests do not address a DO directly in this configuration.

On reconnect, the public route authenticates again. Once accepted, both objects attach only identity (plus username for chat) to the socket and restore that attachment on hibernation. They retain no session ID/expiry and do not recheck session revocation when processing frames. A Clerk `getUser` call confirms a user record, not the continued validity of that particular session. Exact logout/revocation requirements and deployed cookie behavior need a two-session staging test.

The application uses default broad CORS and does not validate the WebSocket `Origin`. This is a configuration gap, not a demonstrated cross-site authenticated exploit: CORS itself does not govern WebSocket upgrades, and Clerk/cookie/browser behavior must be tested. The hosted app and Vite proxy use same-origin API/WS URLs. Specify allowed hosted/dev origins and verify actual staging requests before calling origin handling complete.

## Secret-copy lifecycle and environment isolation

Runtime secret bindings exist in generated `Cloudflare.Env`. Current setup RPC sends the Clerk secret as an argument and writes one copy per battle/chat object under `clerkSecretKey`. Cold start depends on that copy even though only battle ID/builds/history/delivery need persistence. Chat's `storage.put` is not awaited. No TTL or deletion is implemented for either key. Existing objects and retained storage backups therefore require an explicit rotation/removal disposition; no contents were inspected.

Wrangler declares one Worker name/custom domain, one KV namespace with `experimental_remote: true`, two DO bindings and one workflow. No named staging/production environment split is declared in that file. This proves only that local configuration does not establish isolation; it does not prove remote resources are shared. Remove remote KV use from ordinary local execution or make that use explicit and target-verified. Environment-specific runtime objects, workflow, Clerk, database, assets and telemetry remain a release gate.

At the initial review, client `build` used `doppler run -c prd`; server scripts exposed production dev/schema/deploy commands. The parallel Phase A tooling work is replacing ordinary build/check paths. Recheck final scripts and emitted assets after that work; passing a local build must not imply that production secrets were required or that deployment occurred. Vite source exposes the Clerk publishable key intentionally. This review did not inspect secret values or infer that an exposed publishable key/telemetry DSN is a secret leak.

## Reproducible probes and regression proposals

The temporary isolated access probe executed real `appRouter.createCaller` calls against `tests/battle/support/database.ts` with users `audit-owner` and `audit-outsider`:

1. Seed owner character with two unspent points; outsider calls `character.applyStatIncrease({ characterId: "audit-hero", stats: ["strength"] })`. Observed remaining points `1`, strength `19` (from `18`). Expected after repair: rejection and byte-equivalent row.
2. Seed outsider-owned `armor-up`; outsider calls `character.equipPassiveSkill({ characterId: "audit-hero", passiveSkillId: "outsider-passive" })`. Observed passive assigned to the owner hero. Expected after repair: rejection and unassigned passive.
3. Outsider calls legacy `dungeon.getDungeon` and then `dungeon.getRun` for the same ID. Observed legacy success and new-view `This run belongs to another party`. This is documented visibility inconsistency, pending policy.
4. Execute real `BattleChat.webSocketMessage` with an eight-byte `ArrayBuffer`, persist through an in-memory platform adapter, then reconstruct the class. Observed stored non-string and cold-start rejection. The probe passed its two assertions under Bun 1.4.0. Expected after repair: invalid frame rejected without persistence, legacy malformed records safely omitted.

Permanent regressions belong in a new `tests/battle/integration/security-access.test.ts` and any clearly named new chat/runtime test file; do not modify the 34 protected historical files. Cover creator/participant/outsider rights, verified query overwrite at the upstream boundary, unknown actions, payload/history caps, legacy secret deletion and synthetic telemetry redaction. Existing command/recovery and dungeon tests remain regression evidence but do not establish real Cloudflare/Clerk behavior.

Before release, run the same ownership and reconnect cases through two authenticated browsers on staging, test missing/expired/revoked sessions, verify origin handling and resource namespaces, inspect the final bundle for server-only configuration/debug fixtures, and confirm diagnostics/retention in the actual telemetry project. Until those checks have evidence, Phase D is incomplete.

## Local remediation results

The following repairs are committed in code candidate `4ae05e3`. The preceding findings and permission matrix deliberately retain the captured pre-fix evidence; their unresolved policy labels describe the baseline, not new release work. Existing cooperative party assembly, authenticated spectator reads/posts and public replay visibility remain the accepted behavior. Unlimited manual spell grants are development/testing only.

- Stat allocation receives verified user identity, rejects outsiders, and locks the character before reading points. Passive equipment now verifies both owners. Passive direct transfers retain existing behavior while locking source and target characters in database collation order. Spell/equipment/passive removal uses the same character-before-item order as frozen build capture, rereads the assignment after locking, and returns `CONFLICT` on a concurrent move. Wrong-owner spell removal remains a silent no-op. XP grants now lock the character without changing level-up calculations. Attempt capture, route decisions, completion and passive transfers share `lockCharacters`, using SQL `ORDER BY id FOR UPDATE`. A review caught that JavaScript `localeCompare` disagreed with database ordering for `a`/`B`; the new mixed-case regression verifies the common database order and that frozen builds survive direct passive transfers.
- Chat rejects binary, oversized and empty input before persistence. Cold initialization removes malformed legacy history. Successful history commits precede in-memory state and broadcasting; a write failure does not publish a message. Server and client retain at most 50 messages and at most 64 KiB of encoded JSON. The control-character regression measures actual encoded size, including JSON escape expansion.
- Battle ingress rejects binary/oversized frames before parsing or queueing. Per-socket windows allow 30 battle messages or five chat messages per ten seconds. Windows persist in WebSocket attachments across hibernation. Each room admits at most 32 sockets, with at most four per identity. Invalid command recovery is sent to the requester, so it cannot trigger a full-room state broadcast. These are conservative initial operational budgets, not a claim of measured staging throughput; real runtime/device qualification remains open.
- Public battle/chat routes require a WebSocket upgrade, reject cross-origin browser requests, and verify that a battle attempt, frozen start or saved result exists before object setup. Each handshake uses a PostgreSQL client capped at one connection, with a three-second connect timeout and five-second connection lifetime, and closes the client in `finally` for success, missing battles, and read/write failure. The hosted same-origin path and the local Vite proxy on `localhost`/`127.0.0.1`, ports 3000/3001, remain allowed. Existing authenticated spectator reads/posts and public replay visibility remain the accepted baseline.
- Both Durable Objects construct Clerk clients from runtime `CLERK_SECRET_KEY`. Cold initialization and setup overwrite the legacy storage value with `null`, erasing the copied credential while preserving compatibility with the protected minimal storage adapters. The physical key is a harmless tombstone. The old two-argument setup signature remains temporarily supported for rolling RPC callers, but ignores their key. New upstream requests send only the battle ID. Journal version `1` is explicit; absent legacy markers mean version 1, unknown markers fail before reconstruction, and saved build arrays pass `decodeStartingBuilds` validation.
- User creation and the three starter grants commit together; a conflict-safe user insert chooses the single provisioning request. Existing users keep the read-only fast path. New regressions exercise overlapping first requests and a failure on the second starter spell. Existing accounts with an old partial starter grant are not silently regranted items; any repair needs an account-specific audit.
- The user resolved the manual spell-grant policy as development/testing only. The `createSpell` procedure now requires the runtime `DOPPLER_ENVIRONMENT` binding to equal `development` or `test`; production, staging, missing, empty and other values fail with `FORBIDDEN` before the grant transaction. Authentication remains required. Permitted calls retain the same seven spells and transaction behavior; automatic starter spells are unchanged. Production UI hides the manual action separately, while the server guard enforces the restriction for direct RPC callers.
- Server telemetry runs only for explicit `DOPPLER_ENVIRONMENT` values `production` or `staging`; local templates use `development`. Server and client disable default PII and sanitize exception events before delivery, dropping request/user/query/body/breadcrumb/context/extra/error-message data while retaining source locations. Server request-URL logging and raw error logging are removed. Closed structured events cover request/RPC failure, rejection, recovery and completion delivery retries. No synthetic telemetry was transmitted.
- `/api/healthCheck` remains public liveness; `/api/ready` separately validates required configuration and a database `select 1`, returning only readiness and status 200/503. Its PostgreSQL probe uses one connection, a three-second connect timeout, a five-second maximum connection lifetime, and closes its client in `finally` on success or failure. tRPC request bodies have a 64 KiB application limit, including streamed bodies without `Content-Length`. This does not establish Clerk, DO or workflow readiness; their real staging checks remain required.

New executable evidence is in `security-access.test.ts`, `chat-security.test.ts`, `durable-security.test.ts`, `server-security-boundary.test.ts`, `development-spell-grants.test.ts`, and `character-locks.test.ts` under `tests/battle/integration/` (24 passing tests). It verifies outsider/anonymous rejection, passive ownership/transfer, mixed-case lock ordering, legacy chat repair, encoded history limits, hibernation-preserved ingress limits, storage failure behavior, runtime-key use/legacy erasure, journal version rejection, saved-build validation, connection caps, verified upstream identity propagation, missing battle rejection, local proxy origins, declared and streamed request size rejection, readiness/handshake failure/client cleanup, development-only manual grants, provisioning atomicity and synthetic redaction. The existing protected Durable Object (8), equipment (3), dungeon attempt (10), branching route (11), and complete-run (6) suites also pass in focused runs after the relevant changes. Application typechecks pass; the parent evidence records the separate protected historical type diagnostic disposition and complete release gate.

The separate database rehearsal now covers real PostgreSQL contention, including mixed-case lock ordering, passive transfer and unequip versus snapshot capture, and overlapping XP grants. Release still requires real Clerk logout/revocation, staging hibernation/alarm/workflow retry, browser/session acceptance, dependency disposition, and deployment/telemetry isolation proof.
